# 文档体系设计与规范（v2）

> 本文是笔记库的「宪法」：目录怎么分、笔记怎么写、怎么发布到线上站点。改规则先改这里。
> v2 相对 v1 的核心变化：**把「站点卡片」确认为权威内容形态，笔记库反向对齐站点分区**，并补上可执行的同步链路。

## 〇、先看清两侧的真实结构（2026-09-16 实测）

做设计前必须先承认一个事实：**你现在有两套并行的内容体系，而且它们是「倒挂」的。**

### A. 线上站点（`D:\workspace\my-agent-lab`）

| 项 | 现状 |
|---|---|
| 内容形态 | **能力卡片（card）**，45 张 |
| 唯一数据源 | `backend/content/*.md`（一篇 md = 一张卡） |
| 索引文件 | `backend/content/tags.md`（权威目录：声明分区 → groups → 卡片 id 顺序） |
| 读取方式 | 后端 `app/api/content.py` **每次请求实时读盘解析**，改 md 后刷新页面即生效，无需重启 |
| 分区（7 个） | `agent-engineering` 工程演进 / `agent` 范式 / `rag` / `protocol` / `eval` / `ops` 生产治理 / `ml` 机器学习 |
| 知识卡 vs 能力卡 | `experience: false` = 纯知识卡（隐藏「立即体验」按钮）；否则为可跑的能力卡 |
| 站点仓库 | `git@github.com:zzm921/my-agent-lab.git`（master） |
| 部署 | `start.sh` / `start.bat`：前端 `npm run build` → 后端 `uvicorn app.main:app --port 8000` |

**站点侧关键约束**：站点只认 `{分区} → {卡片}` 两层，卡片 id 必须是 `kebab-case` 英文，正文用 `##`/`###` 分节，**不渲染 `[[双链]]`**。

### B. 笔记库（`D:\workspace\my-note`）

| 项 | 现状 |
|---|---|
| 规模 | 181 篇 md（技术学习 135 + 日报 38 + 其他 8） |
| 组织 | 旧的 `技术学习/` 单层大杂烩，未按 Domain 分层 |
| 同步机制 | **不存在**。笔记和站点内容各写各的（如 ML 笔记与 `ml-*.md` 是两份） |
| 版本管理 | `git@github.com:zzm921/my-note.git`，Obsidian Git 插件自动提交 |
| 附件 | 库根 `images/`（78 个）+ `.gitbook/assets/`（11 个），两处并存 |

### C. 诊断：不一致的四个具体表现

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **同一主题两份内容，无主次** | `技术学习/机器学习/4_分类与逻辑回归.md` ↔ 站点 `ml-classification-logistic-regression.md`（17KB，更新于 9-16）；`技术学习/rag/01~05-*.md` ↔ 站点 `naive-rag/advanced-rag/modular-rag.md` | 不知道改哪份，两边逐渐分叉 |
| 2 | **站点是「成品」，笔记库是「原料」** | 站点 45 张卡结构完整（H1 概览 + 分节 + 表格）；笔记库 135 篇中大量是无 H1/H2 的粘贴稿、0B 空文件 | 笔记无法直接发布，站点内容无法反哺笔记 |
| 3 | **分区维度不统一** | 站点 7 分区是「AI 技术域」；笔记库同级混着「技术栈」（node/docker）+「学科」（机器学习）+「用途」（面试题/CICD） | 无法建立一一映射，发布时靠人肉判断 |
| 4 | **无发布标记** | 全库仅 7 篇有 frontmatter，无 `site` / `status` 字段 | 无法自动判断哪篇该上站，同步只能全量手工 |

> **结论**：不要在旧结构上打补丁。正确解法是——**确立「站点分区」为顶层骨架，笔记库围绕它重组；并明确「谁是谁的源」。**

## 一、核心决策：谁是唯一源？

这是整套设计里最重要的一个问题，必须先在两种模式里选一个。

### 模式 A（推荐）：单一主库 = 笔记库，站点是产物

```
my-note/（Obsidian，唯一写作入口）
   └── 发布同步脚本 ──► my-agent-lab/backend/content/*.md（站点读取）
```

- 优点：只写一处；Obsidian 里能双链、能图谱、能日志；站点内容永远追平笔记。
- 代价：需要一条**同步脚本**（本方案已给出设计，约 150 行 Python）；笔记必须严格遵守规范才能发布。

### 模式 B：站点为主，笔记库只做学习笔记

- 站点卡片直接在 `my-agent-lab` 里维护；笔记库纯自学、不上站。
- 优点：零脚本、零同步风险。
- 代价：知识沉淀与展示彻底割裂，站点内容无法复用笔记的积累。

> **本方案的推荐是模式 A**，理由是你明确表达了「笔记要同步到线上」——那笔记就必须是源。
> 如果你更想省事，可以退化到「模式 A-lite」：**只让 ML / RAG / Agent 这些成体系的主题走同步**，其余旧笔记留在库里不上站。

## 二、设计原则（六条）

1. **一层只用一个维度**：顶层按「**站点分区优先，学科兜底**」；技术域内部不再出现「面试题」「docker」这类用途或工具名当一级目录。
2. **一篇笔记只属于一个目录**：跨域关系用 frontmatter 的 `tags` / `domain` 表达，不复制文件。
3. **深度封顶三级**：`域 / 子域 / 笔记`。禁止 `node学习node基础/xxx` 这种「学习+技术」重复嵌套。
4. **命名机器友好**：文件名 = 标题，**不含空格**（用 `-`），序号只用 `NN-` 一种前缀，卡片 id 全小写 `kebab-case`。
5. **收件箱机制**：新笔记先扔 `00-Inbox/`，允许乱——但只有这一个地方能乱，每周清一次。
6. **归档而非删除**：过期提纲、碎片、旧版本进 `99-Archive/`，保留 git 历史。
7. **发布是显式动作**：只有 frontmatter 写 `publish: true` + `site: xx` 的笔记才上站。**默认不发布。**

### 3.1 为什么顶层是 `10/20/30...80` 而不是中文名？

- 数字前缀强制排序，Obsidian 文件树里结构一眼可见；
- 给未来留插入空间（`15-`、`25-`）；
- `00` / `99` 天然的「入口 / 出口」语义。

## 四、文档结构规范

### 4.1 统一 frontmatter（同时服务 Obsidian 与站点）

```yaml
---
# —— 笔记库字段（所有笔记都要）——
type: concept            # concept | tutorial | howto | issue | moc | daily | project
domain: 10-AI/rag        # 主题域，与所在目录一致
tags: [RAG, 检索, Rerank]
status: draft            # draft | living | done | archived
created: 2026-07-01
updated: 2026-09-16
source: 课程/文章链接      # 可选

# —— 发布字段（只有要上站的笔记才写）——
publish: true            # 默认 false；true = 参与同步
site: rag                # 目标站点分区（agent-engineering|agent|rag|protocol|eval|ops|ml）
cardId: advanced-rag     # 站点卡片 id，全小写 kebab-case，全站唯一
icon: layers             # 可选，卡片图标
difficulty: int          # 可选，beg | int | adv
completeLevel: 90        # 可选，能力卡完成度 0-100；纯知识卡不写
experience: false        # 可选，false = 纯知识卡（隐藏「立即体验」按钮）
featured: false          # 可选，置顶
new: false               # 可选，标记新技术卡
techFilters: [LangGraph] # 可选，站点技术筛选
accent: '#7c5cff'        # 可选，卡片主题色
mode: react              # 可选，跳实验室的模式 id
strategy: cot            # 可选，prompt 策略
enabledTools: [rag]      # 可选，进入实验室自动启用的能力
prompts:                 # 可选，预设任务
  - 帮我计算 2 的 10 次方
faults: {calculator: off}# 可选，故障注入
---
```

**字段分层记忆法**：上半部分（`type` → `source`）是给「人」看的；下半部分（`publish` 起）是给「站点」用的。
只写上半部分的笔记 = 纯私人笔记，永不上站。

### 4.2 正文骨架（硬性要求）

```markdown
# 标题                       ← 第一行必须 H1，不带序号前缀

> 一句话说明本文覆盖什么：要点A、要点B、要点C
                              ← H1 后紧跟一行引用块，会成为站点 shortDesc

## 第一节
## 第二节
### 小节（最多到 H3）
```

**三条铁律**：
1. 第一行是 H1，**全文只有这一个 H1**（站点卡片正文从 `##` 开始渲染）。
2. H1 后紧跟 `> 摘要行`，一句话说清覆盖范围 —— 既是站点卡片描述，也是自己复习的抓手。
3. 分节只用 `##` / `###`，不允许「无标题大段粘贴」。

### 4.3 六种笔记模板（放 `_Templates/`）

**① concept 概念卡**（术语、机制、原理）
```markdown
# 逻辑回归
> 二分类的概率模型：为什么线性回归不适合分类、Sigmoid、对数损失、决策边界。
## 定义
## 为什么需要它 / 解决什么问题
## 关键机制（公式 + 直觉解释）
## 与相邻概念的区别（对比表）
## 易错点
## 小结
```

**② tutorial 教程 / 课程笔记**（成体系的学习笔记）
```markdown
# 神经网络
> 本文覆盖：感知机 → 多层网络 → 反向传播 → 常见激活函数。
## 概述（本课在整门课中的位置）
## 概念与公式
## 手算示例
## 代码示例（可运行）
## 常见坑
## 小结与下一步
```

**③ howto 实操手册**（命令、配置、部署）
```markdown
# Nginx 反向代理 WebDAV
> 场景一句话 + 前置条件（版本、依赖）。
## 目标与前置条件
## 步骤（1/2/3，每步含命令与预期输出）
## 验证方法（怎么确认成功）
## 回滚 / 排错
```

**④ issue 踩坑记录**（故障与排查）
```markdown
# 服务器连接被重置（Connection reset）排查
> 现象一句话 + 最终结论一句话。
## 现象与影响面
## 排查过程（按时间线，含证据：日志/抓包）
## 根因
## 解决与验证
## 教训（下次如何更快定位）
```

**⑤ moc 地图 / 索引页**
```markdown
# AI · Agent 地图
> 本域包含哪些子主题、先看哪几篇、与站点的对应关系。
## 学习路径（按顺序列出笔记链接）
## 按子主题分组（[[笔记名]]）
## 待补 / 待重写清单
```

**⑥ daily 日报**（沿用现有 AI热点日报格式，放 `90-Daily/2026/YYYY-MM-DD.md`）

### 4.4 命名与排序

| 场景 | 规则 | 示例 |
|---|---|---|
| 有顺序的课程/系列 | `NN-标题.md`（两位序号） | `01-机器学习导论.md` |
| 单篇主题笔记 | `标题.md` | `Redis持久化机制.md` |
| 要发布的笔记 | 文件名建议直接用 `cardId` | `advanced-rag.md` |
| 目录 | 名词、无空格、无「学习」等冗余词 | `node/`、`mysql/`（不要 `node学习node基础/`） |
| 禁止 | 空格、双空格、`--`、中文括号、大小写混排 | ~~`Rag 评估.md`~~ → `RAG评估.md` |

### 4.5 附件与双链

- 图片统一放 `99-Attachments/`（可按年份分子目录 `99-Attachments/2026/`），正文用**相对路径**引用。
- 双链 `[[笔记名]]` **只在库内使用**；站点不渲染 `[[ ]]`，同步脚本必须把它转成普通文本。
- 迁移时同步改写正文里的图片路径；逐步废弃库根 `images/` 与 `.gitbook/assets/`。

## 五、发布链路设计（笔记 → 线上服务器）

### 5.1 数据流

```
① 写笔记             my-note/10-AI/rag/advanced-rag.md
                      frontmatter: publish: true, site: rag, cardId: advanced-rag
                          │
② 同步脚本           scripts/sync_to_site.py
   ├─ 扫描全库，筛选 publish: true
   ├─ 校验：cardId 唯一 / site 合法 / H1 存在 / 摘要行存在 / 无 [[双链]]
   ├─ 转换：去掉发布字段，重写为站点 frontmatter，剥掉 H1，图片路径改写
   └─ 生成：my-agent-lab/backend/content/<cardId>.md
                          │
③ 更新索引           按 site 分组重新生成 tags.md 的 cards 列表
                          │
④ 提交 & 推送         git commit + push（两个仓库各自提交）
                          │
⑤ 部署到服务器         服务器 git pull → npm run build → 重启 uvicorn
```

### 5.2 同步脚本要做的事（`sync_to_site.py`）

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 扫描 | 遍历库内 `*.md`，读 frontmatter | 无 frontmatter → 跳过 |
| 筛选 | 取 `publish: true` 且 `status != archived` | — |
| 校验 | `cardId` 必填且全库唯一；`site` 在白名单内 | **报错并终止**，列出问题文件 |
| 校验 | 正文有且仅有一个 H1；H1 下有 `>` 摘要行 | 报错，提示补写 |
| 剥离 | 删除 `publish/site/cardId/domain/status/created/source` 等库内字段 | — |
| 改写 | `[[X]]` → `X`（纯文本）；图片路径 → 站点可用路径 | 图片文件一并复制到站点静态目录 |
| 落盘 | 写 `backend/content/<cardId>.md` | 覆盖前打印 diff 摘要 |
| 索引 | 更新 `tags.md`，保持分区/groups 结构与现有顺序 | — |
| 报告 | 输出：新增 N / 更新 M / 跳过 K / 错误 E | 有错误时退出码非 0 |

**关键设计取舍**：脚本**只写、不删**站点里的卡片（避免误删手工维护的 `experience: true` 能力卡）；站点侧的 `completeLevel`、`faults`、`prompts` 等「可跑配置」字段，允许笔记里不写，由脚本**保留目标文件已有值**。

### 5.3 部署到线上服务器

站点是「前端静态产物 + FastAPI 后端」的形态，推荐两种方式：

**方式一：服务器手动/脚本部署（简单直接）**
```bash
# 服务器上
cd /srv/my-agent-lab && git pull
cd frontend && npm ci && npm run build
cd ../backend && source .venv/bin/activate && pip install -r requirements.txt
sudo systemctl restart agent-lab        # 或 kill 后重新 nohup uvicorn
nginx -s reload                         # 若由 nginx 托管前端
```

**方式二：CI 自动部署（推荐，长期）**
- 仓库加 GitHub Actions / 内网 GitLab CI；
- 触发条件：`backend/content/**` 或 `frontend/**` 变更；
- 步骤：`npm ci && npm run build` → `rsync` 产物 + `backend/` 到服务器 → `systemctl restart`。

**内容热更新的优势**：因为 `content.py` 是**每次请求实时读盘**，所以**只改卡片正文时，服务器上连重启都不需要** —— `git pull` 完刷新页面即生效。这条特性应作为日常更新的主路径：

> 日常更新内容 → 只需 `git pull`（无需 build、无需重启）
> 改了前端代码 → 需要 `npm run build`
> 改了后端代码 → 需要重启服务

### 5.4 三种更新场景对照

| 场景 | 需要做什么 | 耗时 |
|---|---|---|
| 改卡片正文 / 加新卡片 | 本地 sync → push → 服务器 `git pull` | 秒级 |
| 改卡片的可跑配置（mode/prompts/faults） | 同上 | 秒级 |
| 改前端 UI / 后端逻辑 | 上面 + `npm run build`（前端）或重启（后端） | 分钟级 |

## 六、实施路线（建议顺序）

| 阶段 | 动作 | 风险 | 验证方式 |
|---|---|---|---|
| **S1** 建骨架 | 建 `00-Inbox/` `01-Maps/` `_Templates/` `99-Archive/`；落地六套模板 | 极低（只增不改） | 目录存在、模板可套用 |
| **S2** 清噪音 | 0B 空文件、旧提纲、被替代版本移入 `99-Archive/`（先出清单再动手） | 低 | 归档清单经你确认 |
| **S3** AI 域对齐 | `10-AI/*` 七个分区与站点一一对应；把站点现有 45 张卡的正文**反向回填**进库 | 低 | 库内每篇可对应一张站点卡 |
| **S4** 补 frontmatter | 给回填后的笔记加 `publish/site/cardId`；跑脚本做首次全量同步 | 中 | `tags.md` 与库内一致 |
| **S5** 技术学习分区 | 剩余 `技术学习/` 按 `20~60` 重排（dry-run 预览 → 逐目录执行） | 中（路径变；`[[双链]]`按文件名解析不受影响，md 路径链接会失效，脚本先扫描报告） | 抽查 10 篇链接有效 |
| **S6** 自动化 | 同步脚本 + CI 部署打通；Obsidian 里加一个「发布」快捷命令 | 低 | 改一篇笔记 → 线上刷新可见 |

> **S3 是最关键的一步**：它一次性解决「同一主题两份内容」的问题——把站点的成品正文回填进库，此后**库是唯一源，站点是产物**，分叉不再发生。

## 七、每篇笔记的检查清单

发布前逐条自查：

- [ ] 文件名无空格，`NN-` 前缀只用于有序系列
- [ ] 第一行 H1，且全文只有一个 H1
- [ ] H1 后紧跟 `> 摘要行`
- [ ] 分节只用 `##` / `###`，无「无标题粘贴」段落

- [ ] 要发布的：`publish: true` + `site` + `cardId` 已写，`cardId` 全库唯一
- [ ] 正文无 `[[双链]]`（或已确认会被脚本转换）
- [ ] 图片在 `99-Attachments/`，路径为相对路径
- [ ] 归属目录唯一，未跨域复制
