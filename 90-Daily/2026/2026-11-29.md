**arXiv：给模型「讲理论」比给同长度例题更值钱**
在长度对齐的实验里，把正确的理论写进上下文，Qwen3-14B 在等待时间问题上的 pass@1 从 0.37 提到 0.83，正确解的中位 token 从 10.2k 降到 6.3k；同长度的工作示例没有这个效果。模型越强、token 预算越大，增益越小（+0.46 → +0.07）。
对 Agent：写 system prompt / skills 时优先给「可执行的原则和判据」，少堆 few-shot 示例——模型自己会省下试错的 token。
https://arxiv.org/abs/2611.34751

## 🧩 Agent 开发

**Google DeepMind 工程师的 Gemini 4 Neon 五改：先删旧规则**
Philipp Schmid（Google DeepMind Staff Engineer，负责开发者体验）给出的第一条就是清理过时、重复、互相打架的规则——用户级/项目级/当前任务三层规则长期叠加，会互相抑制并持续烧 token。另外两条可直接照搬：长对话压缩前，让模型在每个阶段末写下目标、关键决定和文件路径，再开新会话接着干；工具定义里删掉示例，只留接口规则，避免模型机械照搬示例出错。
今天就能做：把你 agent 的 `AGENTS.md` / 系统提示过一遍，删掉不是为当前模型写的补丁式限制。
https://www.qbitai.com/2026/11/513555.html

**Claude Code 任务框定初步实验：同一任务，描述方式一变成本就涨**
HN 580 分。对同一个 GPU kernel 优化和 nanoGPT 修 bug 任务，改动指令里关于「模型开发」和「人工审查」的描述，Claude Code 在两个任务上轮数都变多，kernel 实验耗时更长；KernelBench 上的质量差异跨轮次不稳定，但执行成本的上升是稳定复现的。nanoGPT 那组每次都能找到同一个修法。
对 Agent：把「轮数 / 执行成本」当作和通过率并列的评测维度，否则 prompt 里一句无害的措辞就能让账单翻倍。
https://xinyadu.github.io/blog/claude-code-sabotage.html

**多智能体编排两个新工具：Fleetlayer 与 SessionGraph**
Fleetlayer（HN 23 分/14 评）解决「在多台机器上跑大量 Agent」的调度与分发；SessionGraph 把多个编码 Agent 的会话汇成一张可交互的图，用来定位哪一步跑偏。
对 Agent：一个是横向扩机器的执行层，一个是事后归因的可观测层，正好补齐多智能体最难查的那一块。
https://fleetlayer.ai/ ｜ https://sessiongraph.ai/

**VS Code 1.148：agent 干活时不再让机器睡着**
新增 agent 运行期间阻止系统休眠的机制，长任务不会再因锁屏中断。
对 Agent：本地跑长链任务（数据抓取、批处理、构建）的，升到 1.148 能少一类「跑到一半被挂起」的偶发失败。
https://www.oschina.net/news/503865/visual-studio-code-v1-148

**DoorDash：把生鲜杂货复购的交互延迟从 16 秒压到 2 秒**
InfoQ 报道，改造点是让 Agent 承接用户重复购买时的整段流程，而不是每步都走一次同步交互。

https://www.infoq.cn/article/2uDBVKjk3kJXRb6CqQfu

## 📊 评测与基准

**DRBench Pro：面向专业深度研究 Agent 的知识中心基准**
arXiv 2611.34832。与「答对几道题」不同，它按知识获取—组织—使用的链条评分，覆盖需要多轮检索与整合的专业研究任务。
对 Agent：做 research / deep-research Agent 的，可用它定位瓶颈到底在检索、整合还是最终成文，比单一通过率更能指导改动。
https://arxiv.org/abs/2611.34832

**μ-Bench：共享交互语音 Agent 的多用户任务完成基准**
arXiv 2611.34852。测的不是单人一问一答，而是多个用户在同一段语音会话里交替下达任务时，Agent 能否正确归属、串起上下文。
对 Agent：做语音端 Agent 或多人协作场景的，这是目前少见的「多用户共享上下文」评测口径，可直接借用它的任务切分。
https://arxiv.org/abs/2611.34852

## 💰 成本与基础设施

**Google 开源 TPU Sync，Prefill/Decode 解耦的 KV 传输延迟大降**
原生 C++ 库，在 TPU HBM、主机 DRAM、共享存储与数据中心网络之间搬运 KV 缓存块和模型权重。Qwen3 235B 的 KV 传输中位延迟从数秒降到约 230ms，低并发下 TTFT 降 60%，480B 降 90%；64K 上下文前缀缓存场景 TTFT 最高降 90%。同时发布 TPU 8tx / 8i Max 系统。
对 Agent：这是「长上下文 + 高并发」的成本解法——上下文越长，缓存搬运越成为瓶颈。注意 API 尚不稳定，只有开发版 wheel，且需匹配未公开的 torch_tpu 构建。
https://www.infoq.cn/article/MrxlyksI1KxvEKLuCg5P

## ⚠️ 安全与踩坑

**GGUF 聊天模板投毒：327 万个 HF 仓库扫出 5 个恶意模型，2428 次下载**
每个 GGUF 都带一个运行时会对每条 prompt 施加的 chat template，投毒就藏在这儿：模型回答看起来正常，模板却悄悄追加用户看不见的指令（让 Agent 执行 PowerShell 命令，或让每条回复都以一条「请运行」的命令开头）。最强形态是把恶意程序追加在最后一个 tensor 之后——加载器根本不读那段——事后再把模板改成让它打印解包命令。第二个 campaign「timdedid」专门针对编码 Agent。
今天就能做：本地模型只从官方或可信机构仓库拉，下载后检查 chat template 与文件尾部是否存在多余字节；用第三方量化版前先看是谁转的。
https://malspark.com/blog/malicious-gguf-models-hugging-face/
