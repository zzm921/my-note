## 🤖 大模型

**混元 Hy4 flash：100 万上下文、每 token 激活约 12B，单任务成本约为旗舰 Hy4 的 1/20**
姚顺雨与混元团队在 Reddit AMA 里给了实测口径：Hy4（11-04，文本+图像+视频，主打长程软件工程）做旗舰，Hy4 flash（11-16）打速度与成本，按内部评测 WorkIndex 测算，flash 单任务成本约为旗舰的 1/20；两款权重都已公开。HF 镜像趋势榜上 tencent/Hy4-flash 已 ↓6617 / ♥578。
对 Agent 的含义：这是典型的「便宜执行层 + 贵规划层」组合 —— flash 承接工具调用、意图路由、长文档读取（1M 上下文），旗舰只留规划。团队称 96GB 显存能跑 flash（部分专家层与 Engram 查表模块可挪到系统内存），llama.cpp 适配在做、尚未合入。
https://hf-mirror.com/tencent/Hy4-flash ｜ https://www.qbitai.com/2026/11/511757.html

**GPT-6.2 Astra：16 项具身任务成功率较上一代翻倍**
（⚠️ 厂商自评口径）多模态到动作链路的指标又抬了一档。对 agent 的意义不在跑分，而在 GUI / 机器人操作这类「看清楚再点、再动」的任务上，纯视觉驱动的成功率在逼近可用下限。
https://www.qbitai.com/2026/11/511779.html

**arXiv：后训练改变了模型「读出」自身表征的方式**
论文对比 post-training 前后的表征可探性，结论是模型内部仍编码了某类信息，但用旧探针读出来会偏。对做 agent 内部监控/置信度估计的人：linear probe 类监控要在你实际部署的（已后训练）模型上重训，别拿 base 模型上训好的探针直接用。
https://arxiv.org/abs/2611.26510

## 🧩 Agent 开发

**Karpo Decision 31B 与浏览器 agent 框架一起开源：把「每一步判断」交给专用决策模型**
MachinePulse 开源 31B 决策模型，Decision Index（300 个模型同榜）总分 73.9 居首、校准误差 2.3%，单题最多同时判断 255 个候选选项；单卡 RTX PRO 6000 上 14 万次请求中位响应 94ms。配套开源 karpo-browser 框架（System 1 + System 2 架构）、27B 的 Act 模型与网页动作评测集 KBB；Browserbase Benchmark v2 102 道核心任务做到 89% 成功率、201 秒、$0.096/任务。
今天就能想的一件事：把「下一步点哪个按钮 / 任务是否完成 / 几十个工具选哪个」从通用大模型里摘出来交给决策层，规划仍走大模型 —— 延迟与 token 都降一个量级。
https://www.qbitai.com/2026/11/511791.html

**Linger：前 DeepSeek-V1 作者开源的个人 Agent，本地优先**
Tony Zhang（DeepSeek V1 作者、DeepSeek-VL 负责人）公开创业项目 Linger：优先做 PC 端 agent，直接操作已有网页/邮箱/日历，不折腾登录凭据；开源、可接第三方模型。核心 Agent「Another Me」每晚把收件箱、日历、聊天、会议整理成本地 Wiki 当记忆中枢，LoCoMo 长期记忆准确率 95%（称高于 Mem0/MemOS）；主动提醒按重要性与紧急度排期；从反馈里学规则叫「隐式强化」（连续两次「不用告诉我」就静默）。
可抄的两件事：夜间批处理把非结构化信息沉淀成结构化知识库；用「用户是否认账」当奖励信号生成提醒规则。它宣称 RTX 3060 12GB 能跑 125B 的 Qwen3.8-Flash-Next、45.5 tok/s（应含内存卸载，自己实测为准）。
https://www.qbitai.com/2026/11/511570.html

**Show HN：agent-mcts —— 把蒙特卡洛树搜索套在 Claude Code 上**
思路是把一次编码任务展开成多分支（不同改法各跑一遍），用 MCTS 的选择/回传决定继续哪个分支，而不是单条链走到底。项目还小（HN 15 分），价值在骨架：怎么把 coding agent 的每一步包成可回滚节点、没有显式 reward 时怎么用测试通过率当价值函数。
https://github.com/natsu0529/agent-mcts

**InfoQ：Entire Git Forge —— 为编码智能体重构 Git 协作方式**
讲现有 Git 协作模型（人写 commit、人评审 PR）在 agent 高频提交下失配，需要新的分支/评审/归属语义。自建 coding agent 平台的话，这篇当「流程改造清单」读。
https://www.infoq.cn/article/6swrOq5xUXwVqrREwJwc

**InfoQ（AICon 北京）：智能体身份国际标准化进展**
把 agent 的身份、授权与可追溯做成标准体系的实践分享。多 agent 系统里「谁在代表谁调用工具」这条链，可以照着设计。
https://www.infoq.cn/article/721YPdyIZ1D8xz20D22C

## 📊 评测与基准

**GroupAssistBench（腾讯元宝 × KCL）：8 万条群聊、2395 道题，考的不是「记得住」而是「用对谁的哪条记忆」**
50 个真实群聊、80,299 条历史消息，分 L1 记忆召回（1374 题，有确定事实）与 L2 开放式服务（1021 题，按定制 rubric 判分），并按依赖结构分 M1 单条 / M2 多记忆 / M3 更新冲突。最值得记的结论：EverMemOS 在 L1 得 0.621（高于全上下文 0.570），但 L2 只有 0.247（低于全上下文 0.431）—— 检索更准不等于服务更对，冲突更新（M3）才是掉分主因。
数据和代码已开源，可直接拿来压测自己的记忆层。
https://www.qbitai.com/2026/11/511841.html

## 🔥 值得深看

- **Karpo Decision 31B / karpo-browser**：如果你的 agent 每步都在调大模型做「选哪个」，这是能把延迟和成本砍一个量级的架构改动 —— 先量一次自己每任务要几次决策。
- **GroupAssistBench**：记忆评测终于有「服务对不对」这一层，L1 高 L2 低的反差，正好解释为什么很多记忆产品 demo 好看、上线不好用。
- **Linger**：本地优先 + 夜间沉淀 Wiki + 隐式强化，是个人 agent 少见的完整取舍，值得对着自己的记忆方案比一遍。
