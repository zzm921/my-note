## 🧩 Agent 开发

**3. Anthropic 公开 Agent Memory 的工程做法：memory notes + dreaming**
把「Agent 记忆」严格定义为跨会话保留的知识（排除权重更新、单轮 in-context、context compaction），两个组件：① 会话中把显著事件/规则写成 memory 目录下的笔记；② 空闲期「dreaming」回放原始 transcript 去校正这些笔记——因为笔记会写错、也会随环境变化过期。
关键实测数据：CL-Bench 1.0 数据库任务里每个问题都开新会话、唯一共享是持久记忆目录，Opus 5 第一个「闭环」（笔记里同时写规则、规则为何成立、以及踩过的坑），Opus 5.5 / Sonnet 5.5 带记忆后追平 Opus 5；而 Pokémon 测试里 Sonnet 3.7 写了 413 个文件/225 个文件夹只拿 1 枚徽章，Fable 5 只写 9 个文件 + 一个 `global.md` 当仪表盘就拿了 4 枚——**记「屏幕每轮都能读到的状态」是纯浪费，只记策略、计划、验证过的规则**。
最反直觉的一条：告诉模型「记忆是干什么用的」就够，别规定怎么写；「只记录失败」这类硬规则反而让 Opus 5 / 4.7 的增益大幅缩水。今天就能做：给 agent 一个持久 `memory/` 目录 + 一个定时「dream」任务，读日志改写笔记。
→ https://www.anthropic.com/research/components-of-agent-memory

## 📊 评测与基准

**8. 便宜的 judge 先判、拿不准再升级给 Opus：Opus 级准确率、约 1/4 成本**
HN 549 分讨论的级联评审做法：小模型当一线 judge，只在低置信时把样本升级给强模型复核，最终准确率对齐全程用 Opus，成本降到四分之一。对 Agent 最实用的落点是**自动评测和工具返回结果校验**——每个 tool 输出都让 Opus 看一眼太贵，级联是能立刻改的方案。

**9. 论文：把 benchmark 当软件维护（Terminal-Bench 的经验）**
主张基准应当持续迭代任务、像代码一样发版，否则模型很快对着固定题库过拟合。对自建 eval 的启发是：给 eval 集加版本号与「任务老化」机制，别拿一份 2025 年的题单衡量 2026 年的 agent。
→ https://arxiv.org/abs/2611.08412

## ⚠️ 安全与踩坑

**12. ChatGPT 的工具调用被静默路由到另一个 connector，第三方拿到了不该给的数据**
OpenAI 社区的安全 follow-up 帖：多 connector 场景下，一次 tool call 被路由到了不是预期的那个 connector，数据流向由此改变。落地教训很直接：**别只按工具名路由**，要把 server/connector 身份绑进调用，执行前校验目标服务与授权范围；接多个 MCP server 时尤其要防「同名工具」和「兜底路由」。
→ https://community.openai.com/t/security-follow-up-tool-call-silently-routed-to-a-different-connector/1413053

**13. OpenAI 的自动化流程在 Linux 内核里找出 948 个本地提权问题**
规模化代码审计已经到工业级：这类工作以前是人工几周的量。反过来看也是提醒——同一批样本证明了给出内核/root 权限的 agent 能干出什么，跑 Coding Agent 的机器该按「不可信执行环境」设计（容器 + 只读挂载 + 网络白名单）。
