## 🤖 大模型

**1. Maple：Sub-2-BPW 的 MoE 剪枝，把 Gemma 4 26B 压进 6GB 显存、45 TPS**
Show HN 项目（AmSach/maple），做法是对 MoE 的专家做「每权重低于 2 bit」的剪枝，而不是全参数低比特量化，目标是在消费级 6GB 卡上跑 26B 级别模型并保住 45 tokens/s 的交互速度。对做本地 Agent 的人意义直接：**规划/工具调用这类短输出高频调用的环节，本地小卡就能扛**，不必把每次 tool call 都发去云端。注意这是新项目、单点复现，先在自己机器上跑基准再谈替换。
→ https://github.com/AmSach/maple

**2. llama-modchip：284B 的 DeepSeek 在 64GB 内存上跑，无 GPU**
同样是本地推理路线，思路是用内存带宽换显存——把超大 MoE 放在 CPU/RAM 上，靠稀疏激活维持可用速度。适合「离线、数据不出机器」的 Agent 场景（私有仓库理解、内部文档问答），但纯 CPU 下吞吐低，只适合批处理/夜间任务，不适合在线交互。HN 223 分讨论里有实测细节，接之前先看别人复现的 tokens/s。
→ https://github.com/synchopate/llama-modchip

**3. baidu/Unlimited-OCR-2：39 万下载、651 赞，文档摄入这一环可以直接换掉**
HF 镜像上国内机构近期新模型里下载量最高的一个，定位是文档/图像转结构化文本。对 Agent 的价值不在模型本身，而在 **RAG 与工具链的前置环节**：把 PDF、扫描件、截图喂进管线前先过一道 OCR，比让多模态大模型逐页读便宜一到两个数量级。许可与推理成本建议按 HF 页面上的 model card 确认后再批量用。
→ https://hf-mirror.com/baidu/Unlimited-OCR-2

**4. Kimi-K3.1-Pro 稳在 HF 趋势第 2（2.5 万下载 / 1709 赞）**
11-02 发布，一周后仍在趋势前列，说明社区在真实部署而不是只点赞。对 Agent 的实际用法是**长上下文 + 中文工具调用**：长任务里塞完整仓库/日志、或者做中文场景的规划器。上下文越长单价越高，接之前先算清楚每轮对话的固定开销。

## 🧩 Agent 开发

**5. microsoft/TokenEconomizer（★5181）：把 Coding Agent 的 token 成本当黑盒来压**
微软开源的「经验驱动」成本控制器：不改模型、不改 prompt，而是在运行时观察调用模式，学习哪些请求可以直接省掉/降级，属于外挂在 Agent 外面的成本层。对你手上跑批量任务的 Coding Agent 有直接价值——先量出「哪些调用其实是重复的」，再决定要不要动代码。
→ https://github.com/microsoft/TokenEconomizer

**6. Leonxlnx/earshot（★4252）：给 Coding Agent 加一条「听觉」反馈通道，纯 CPU 可跑**
开源项目，定位是让 Coding Agent 能「听、审、发声」——把音频作为输入/校验信号接进 agent 循环，CPU-only 即可运行。目前更适合当实验性输入模态试点（比如语音指令、音频产物自检），别指望它替代主流程的工具调用。
→ https://github.com/Leonxlnx/earshot

**7. InfoQ：自动路由真能省钱吗？便宜模型出错后，人类修一小时可能更贵**
这篇把「按难度路由到便宜模型」的账算穿了：小模型失败后的人工返工、重试与上下文重建成本，经常吃掉单价差。落地建议是**按任务类型而不是按单次请求路由**——确定性高、可自动校验的环节（格式化、抽字段、分类）交给便宜模型；需要多步推理和工具编排的，别省。自建 eval 时要同时记录「重试次数 / 人工介入率」，否则成本曲线是假的。
→ https://www.infoq.cn/article/gOcDmZM2MPAQhWtNb6IJ

**8. InfoQ：Agent 越用越多，企业为什么仍不够 AI Native（11-09 新文）**
同一批 agent 铺开之后的新问题：权限、审计、结果可追溯没跟上，于是每个 agent 都变成需要人盯的孤岛。对工程师的可操作部分在**观测与权限模型**——每个 agent 要有独立身份、可回放的执行记录、以及「能做什么」的显式清单，而不是共享一把管理员 token。
→ https://www.infoq.cn/article/YZx670AAiudsqZjx3UNo

**9. 雷锋网：腾讯的 Agent 布局，不止 WorkBuddy**
企业侧 Agent 平台的完整拼图（办公入口 + 后台编排 + 权限体系）。不需要照抄产品，但它的**分层方式**值得参考：入口层、编排层、连接器层分开，权限在连接器层收口。自己搭内部 agent 时按这个切，后面接新系统不用改 agent 代码。
→ https://www.leiphone.com/category/industrynews/oxR5pn9S7tI1IfF5.html

## 📊 评测与基准

**10. MaxxBench：DeepSWE 分数很好看，但它可信吗（361 分 / 101 评）**
一场对 SWE 类基准的公开质疑：任务污染、评测脚手架差异、以及「分数涨了但真实能力没涨」的可能。对你的直接结论是**别拿单一榜单分数做选型决策**，尤其是禁止联网、固定仓库的 SWE 类数字；自建 eval 时把「同任务多次运行方差」和「脚手架版本」一起记录，否则复现不了。
→ https://maxxbench.unlap.ai/research/why-maxxbench/

## ⚠️ 安全与踩坑

**13. AGENTS.md 已成攻击载荷：网页静默把文件丢进 ~/Downloads，Codex 成功率 >90%、Claude Code 约 50%**
Forever Security 披露并在虚拟机复现的攻击链，逻辑很干净：网页在你没点任何按钮的情况下把一个 13KB 的「团队本地开发环境准备规范」写进下载目录；你随后在该目录起 Codex/Claude Code 让它「整理一下文件」，agent 自动把 AGENTS.md/CLAUDE.md 当成最高指令读进去。针对 Codex 的 payload 会要求在 session 开始前把 tools server 注册到 `~/.codex/config.toml`，并诱导它用 `--dangerously-bypass-approvals-and-sandbox` 起子进程——**写的是全局配置，删掉当前目录也清不掉**。针对 Claude Code 的变体则改 `.claude/settings.json` 里的 `ANTHROPIC_BASE_URL` 指向攻击者网关，下一次请求就把 OAuth token 送出去，再回一个 `dangerouslyDisableSandbox: true` 的 Bash 调用拿终端。还用了零宽字符藏 prompt。
今天就能做的四步自查：
`ls -la ~/Downloads/AGENTS.md ~/Downloads/CLAUDE.md ~/Desktop/AGENTS.md ~/Desktop/CLAUDE.md`
`ls -l ~/.codex/config.toml`（看有没有多出奇怪的 `[mcp_servers.*]`，命令里带 launchctl/curl/临时目录的要警惕）
`ls -la /tmp/ptools`（恶意 npm 包 function-color / function-flag 的落地痕迹）
`echo $ANTHROPIC_BASE_URL` + 翻各项目 `.claude/settings.json`，非自己配的网关地址立刻删。
→ https://www.qbitai.com/2026/11/508244.html

**14. Claude Code 的「Don't Ask Again」把口令写进 1,122 个公开 GitHub 文件**
Apiiro 的审计：用户为了让 agent 别再问，把命令加进允许列表，而这一步会把含凭据的字符串一起写进仓库里的配置文件，随后被推到公开仓库。教训是**允许列表要用通配模式而不是整条命令**（把 `curl -H "Authorization: Bearer xxx" ...` 整行加白，等于把 token 提交了），并且把 agent 的本地配置文件加进 `.gitignore`、定期扫历史。
→ https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again
